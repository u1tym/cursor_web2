# 機能: schedule（スケジュール管理）

## 目的

利用者が自分の予定と TODO をカレンダー上で登録・確認・更新できるようにする。種類・日時の粒度・カテゴリ（色）と、自分用の休日を整え、日単位と時間単位を区別して管理する。

## ユーザーストーリー

- 利用者として、予定と TODO をカレンダーで見たい。なぜなら、いつ何があるかを一目で把握したいから。
- 利用者として、予定と TODO を追加・変更・削除したい。なぜなら、自分の予定を最新に保ちたいから。
- 利用者として、TODO の実施済み／未実施を管理したい。なぜなら、やり残しが分かるようにしたいから。
- 利用者として、カテゴリを自分用に追加・変更・削除し、色を付けたい。なぜなら、種類ごとに見分けたいから。
- 利用者として、見たくないカテゴリを非表示にしたい。なぜなら、今見たいものだけに集中したいから。
- 利用者として、日曜始まりと月曜始まりを切り替えたい。なぜなら、自分の週の感覚に合わせたいから。
- 利用者として、PC とスマートフォンでカレンダーの見せ方を変えたい。なぜなら、画面の広さに合わせて確認したいから。
- 利用者として、今日の月へ戻りたい。なぜなら、別の月を見たあとすぐ現在に戻したいから。
- 利用者として、自分用の休日を年月日と名称で登録したい。なぜなら、会社の休日など、国民の祝日以外もカレンダーで見分けたいから。

## 用語

| 用語 | 意味 |
|------|------|
| スケジュール | 利用者が登録する一件。種別は「予定」または「TODO」。 |
| 予定 | 実施状態を持たないスケジュール。 |
| TODO | 実施済み／未実施を持つスケジュール。 |
| 日単位 | 年月日までで開始と終了を管理する粒度。時刻は持たない。 |
| 時間単位 | 年月日時分までで開始と終了を管理する粒度。秒は持たない。 |
| カテゴリ | 利用者本人が持つ分類。名称と色を持つ。 |
| 論理削除 | データを残したまま、以降の通常の対象外とすること。物理削除は行わない。 |
| 表示対象月 | カレンダーに出している年月。 |
| 週の開始曜日 | カレンダーの左端を日曜にするか月曜にするかの指定。 |
| カテゴリ非表示 | そのカテゴリのスケジュールをカレンダーに出さないこと。カテゴリ自体は削除しない。 |
| ユーザ休日 | 利用者本人が登録する休日。年月日と名称を持つ。日本の祝日とは別である。 |
| 本機能 | このスケジュール管理機能そのもの。メニューへ載せる機能の一つである。 |
| ログ | 操作の入力、判断結果、正常系ではない場合の理由を、タイムスタンプと区分付きで残す記録。画面へ出す文言とは別である。 |

## 要件

要件は EARS の意味を保ち、日本語の文で書く。画面部品、テーブル定義、API パス、HTTP ステータスなど設計は書かない。

### REQ-001

本機能を利用するとき、システムはログインを必須とし、ログイン中ユーザに本機能が割り当てられているときだけ利用を許可すること。

#### 受け入れ条件

- [ ] 未ログインでは、スケジュールとカテゴリとユーザ休日を参照・操作できない。
- [ ] 本機能が割り当てられていないログイン中ユーザは、参照・操作できない。
- [ ] 論理削除済みのユーザまたは本機能では、参照・操作できない。
- [ ] 判定は他機能の API に依存しない。

### REQ-002

システムは、スケジュール・カテゴリ・ユーザ休日・表示設定をユーザごとに保持し、他ユーザのデータは参照させないこと。

#### 受け入れ条件

- [ ] あるユーザのスケジュール・カテゴリ・ユーザ休日・表示設定は、そのユーザ自身だけが参照・操作できる。
- [ ] 他ユーザのスケジュール・カテゴリ・ユーザ休日・表示設定は見えない。

### REQ-003

システムは、スケジュールを「予定」または「TODO」のいずれかとして管理すること。TODO だけが実施済み／未実施を持つこと。

#### 受け入れ条件

- [ ] 予定として登録できる。
- [ ] TODO として登録できる。
- [ ] 予定は実施状態を持たない。
- [ ] TODO は実施済みまたは未実施のいずれかである。
- [ ] 種別を予定と TODO の間で変更できる。
- [ ] 予定から TODO に変えたとき、実施状態は未実施になる。
- [ ] TODO から予定に変えたとき、実施状態は持たなくなる。

### REQ-004

システムは、スケジュールに次を保持すること。タイトル、開始、終了、カテゴリ、場所、詳細、日単位か時間単位か、種別。TODO のときは実施状態も保持すること。

#### 受け入れ条件

- [ ] 上記の項目を保持できる。
- [ ] タイトルは必須である。
- [ ] 開始と終了は必須である。
- [ ] カテゴリは必須である。未削除の、本人のカテゴリだけを指定できる。
- [ ] 場所と詳細は空でもよい。

### REQ-005

利用者が日単位を選んだとき、システムは開始と終了を年月日で管理すること。時間単位を選んだとき、システムは開始と終了を年月日時分で管理すること。

#### 受け入れ条件

- [ ] 日単位の開始・終了に時刻は付かない。
- [ ] 時間単位の開始・終了は分までであり、秒は持たない。
- [ ] 粒度を日単位と時間単位の間で変更できる。

### REQ-006

終了が開始より前になる入力のとき、システムは登録および更新を拒否すること。

#### 受け入れ条件

- [ ] 日単位で終了日が開始日より前のときは失敗する。
- [ ] 時間単位で終了日時が開始日時より前のときは失敗する。
- [ ] 開始と終了が同じときは受け付ける。

### REQ-007

ログイン中の、本機能が割り当てられた利用者がスケジュールを追加するとき、システムは当該利用者のスケジュールとして追加すること。

#### 受け入れ条件

- [ ] タイトル、開始、終了、カテゴリ、粒度、種別を指定して追加できる。場所と詳細は省略できる。
- [ ] TODO として追加したときの実施状態は未実施である。
- [ ] 追加したスケジュールは、当該利用者のカレンダーに出る。

### REQ-008

ログイン中の、本機能が割り当てられた利用者がスケジュールを更新するとき、システムは当該利用者の未削除スケジュールを更新できること。

#### 受け入れ条件

- [ ] 未削除の自分のスケジュールの項目を更新できる。
- [ ] 存在しない、論理削除済み、または他ユーザのスケジュールの更新は失敗する。

### REQ-009

ログイン中の、本機能が割り当てられた利用者がスケジュールを削除するとき、システムは当該スケジュールを論理削除すること。

#### 受け入れ条件

- [ ] 指定した自分の未削除スケジュールを論理削除できる。
- [ ] 削除したスケジュールはカレンダーに出ない。
- [ ] 削除後もデータは残る。物理削除はしない。
- [ ] 存在しない、既に論理削除済み、または他ユーザのスケジュールの削除は失敗する。

### REQ-010

ログイン中の、本機能が割り当てられた利用者が TODO の実施状態を変えるとき、システムは当該 TODO の実施済み／未実施を更新すること。

#### 受け入れ条件

- [ ] 未実施の TODO を実施済みにできる。
- [ ] 実施済みの TODO を未実施にできる。
- [ ] 予定の実施状態は変えられない。
- [ ] 画面が広いときは、日セル上からも実施状態を変えられる。
- [ ] 画面が狭いときは、詳細からは実施状態を変えられず、編集で変える。

### REQ-011

ログイン中の、本機能が割り当てられた利用者がカテゴリを追加するとき、システムは当該利用者のカテゴリとして、名称と色を付けて追加すること。同一ユーザの未削除カテゴリと名称が重複するときは、追加を拒否すること。

#### 受け入れ条件

- [ ] 名称と色を指定して追加できる。
- [ ] 名称は空では受け付けない。
- [ ] 同一ユーザの未削除カテゴリに同じ名称があるときは失敗する。
- [ ] 他ユーザが同じ名称を使っていても追加できる。
- [ ] 論理削除済みのカテゴリと同じ名称なら追加できる。
- [ ] 追加したカテゴリは、当該利用者のカテゴリ一覧に出る。
- [ ] 他ユーザのカテゴリ一覧には出ない。

### REQ-012

ログイン中の、本機能が割り当てられた利用者がカテゴリを更新するとき、システムは当該利用者の未削除カテゴリの名称と色を更新できること。変更後の名称が同一ユーザの別の未削除カテゴリと重複するときは、更新を拒否すること。

#### 受け入れ条件

- [ ] 未削除の自分のカテゴリの名称を変えられる。
- [ ] 未削除の自分のカテゴリの色を変えられる。
- [ ] 名称を空にはできない。
- [ ] 変更後の名称が、同一ユーザの別の未削除カテゴリと同じときは失敗する。
- [ ] 名称を変えずに色だけ変えるときは、同じ名称のままで成功する。
- [ ] 存在しない、論理削除済み、または他ユーザのカテゴリの更新は失敗する。

### REQ-013

ログイン中の、本機能が割り当てられた利用者がカテゴリを削除するとき、システムは当該カテゴリを論理削除すること。紐づくスケジュールは残し、カテゴリとの対応は維持すること。

#### 受け入れ条件

- [ ] 指定した自分の未削除カテゴリを論理削除できる。
- [ ] 削除後もカテゴリのデータは残る。物理削除はしない。
- [ ] そのカテゴリを付けた未削除スケジュールは残る。
- [ ] 存在しない、既に論理削除済み、または他ユーザのカテゴリの削除は失敗する。

### REQ-014

ログイン中の、本機能が割り当てられた利用者が、削除済みカテゴリを一覧に出すかどうかを切り替えたとき、システムはその指定に従うこと。指定は当該利用者の設定として保持すること。

#### 受け入れ条件

- [ ] 出さない指定のとき、削除済みカテゴリは一覧に出ない。
- [ ] 出す指定のとき、削除済みカテゴリが一覧に出る。
- [ ] 指定は再表示しても維持される。
- [ ] 初期状態では、削除済みカテゴリは一覧に出さない。

### REQ-015

ログイン中の、本機能が割り当てられた利用者がカテゴリごとに表示／非表示を切り替えたとき、システムは非表示にしたカテゴリのスケジュールをカレンダーに出さないこと。指定は当該利用者の設定として保持すること。

#### 受け入れ条件

- [ ] 非表示にしたカテゴリの予定と TODO はカレンダーに出ない。
- [ ] 表示に戻すと、そのカテゴリの未削除スケジュールが再び出る。
- [ ] 指定は再表示しても維持される。
- [ ] 初期状態では、未削除カテゴリはすべて表示である。
- [ ] 削除済みカテゴリを一覧に出さないとき、そのカテゴリのスケジュールもカレンダーに出ない。

### REQ-016

ログイン中の、本機能が割り当てられた利用者がカレンダーを開いたとき、システムは表示対象月のカレンダーを示すこと。前月と翌月へ移れること。今日へ戻る操作では、表示対象月を操作している日の年月にすること。

#### 受け入れ条件

- [ ] 開いた直後は、操作している日の年月を表示対象月とする。
- [ ] 表示対象月の年月が分かる。
- [ ] 前月へ移れる。
- [ ] 翌月へ移れる。
- [ ] 今日へ戻ると、表示対象月は操作している日の年月になる。
- [ ] 画面が狭いときに今日へ戻ると、操作している日を選んだ状態になり、その日の詳細が出る。
- [ ] 表示対象月に属する日と、その月の週を埋める前後の日が出る。

### REQ-017

ログイン中の、本機能が割り当てられた利用者が週の開始曜日を日曜始まりまたは月曜始まりに切り替えたとき、システムはカレンダーの並びをそれに合わせること。指定は当該利用者の設定として保持すること。

#### 受け入れ条件

- [ ] 日曜始まりにできる。
- [ ] 月曜始まりにできる。
- [ ] 指定は再表示しても維持される。
- [ ] 初期状態は日曜始まりである。

### REQ-018

システムは、カレンダーの各日に、その日が日本の祝日であるときは祝日名称を付けること。

#### 受け入れ条件

- [ ] 祝日の日には祝日名称が出る。
- [ ] 祝日でない日には祝日名称は出ない。
- [ ] 振替休日を含む。

### REQ-019

システムは、スケジュールを次の順で示すこと。日単位、時間単位の順。同じ粒度の中では開始の昇順。開始が同じときは終了の昇順。終了も同じときはタイトルの辞書順。

#### 受け入れ条件

- [ ] 同じ日に日単位と時間単位があるとき、日単位が先である。
- [ ] 開始が早いものが先である。
- [ ] 開始が同じときは、終了が早いものが先である。
- [ ] 開始も終了も同じときは、タイトルの昇順である。

### REQ-020

開始から終了までに含まれる各日に、システムは当該スケジュールを示すこと。

#### 受け入れ条件

- [ ] 開始日と終了日が同じときは、その日に出る。
- [ ] 開始日と終了日が異なるときは、その間の各日に出る。
- [ ] 表示対象月の外の日にしかかからないスケジュールは、その月の日セルには出ない。

### REQ-021

画面が広いとき（PC 向け）、システムはカテゴリとユーザ休日の操作領域と月カレンダーを同時に示すこと。

#### 受け入れ条件

- [ ] カテゴリ一覧が見える。
- [ ] カテゴリの追加・名称変更・色変更・削除ができる。
- [ ] カテゴリごとの表示／非表示を切り替えられる。
- [ ] 削除済みカテゴリを一覧に出すかどうかを切り替えられる。
- [ ] ユーザ休日の一覧が見える。
- [ ] ユーザ休日の追加・名称変更・年月日の変更・削除ができる。
- [ ] 月カレンダーが見える。

### REQ-022

画面が広いとき、システムは各日に次を示すこと。日付、日本の祝日名称（あるとき）、ユーザ休日の名称（あるとき）、その日の表示対象スケジュール。日付の文字色は、土曜日を青、日曜日および休日（日本の祝日またはユーザ休日）を赤とする。休日と土曜日が重なるときは赤とする。日単位はタイトル。時間単位は、開始日では開始時刻（時分）とタイトル、開始日以外ではタイトルのみ。TODO は実施状態が分かり、実施済みは取り消し線で示す。各スケジュールには、そのカテゴリの色を背景の帯として付ける。表示しきれないときは、残件数を示すこと。

#### 受け入れ条件

- [ ] 日付が出る。
- [ ] 日本の祝日のときはその名称が出る。
- [ ] ユーザ休日のときはその名称が出る。
- [ ] 両方ある日は、両方の名称が出る。
- [ ] 土曜日の日付は青である。日曜日の日付は赤である。
- [ ] 日本の祝日またはユーザ休日の日付は赤である。土曜日と重なるときも赤である。
- [ ] 日単位はタイトルで出る。
- [ ] 時間単位の開始日では `HH:MM` とタイトルで出る。開始時刻はそのスケジュールの開始の時分である。
- [ ] 時間単位の開始日以外ではタイトルのみで出る。
- [ ] TODO は予定と区別でき、実施状態をその場で変えられる。
- [ ] 実施済みの TODO は取り消し線で出る。
- [ ] カテゴリの色が帯として付く。
- [ ] 表示しきれない件数があるとき、残件数が分かる。
- [ ] 残件数から、その日の表示しきれていないスケジュールを参照できる。

### REQ-023

画面が広いとき、利用者が日付を選んだときはシステムは新規スケジュールの追加を受け付けること。表示中のスケジュールを選んだとき、および残件数から出したスケジュールを選んだときは、その編集を受け付けること。日付を選んで追加するときは、開始と終了の初期値をその日とすること。

#### 受け入れ条件

- [ ] 日付を選ぶと、新規追加の入力を始められる。
- [ ] 新規追加の開始と終了の初期値は、選んだ日である。
- [ ] 表示中のスケジュールを選ぶと、その編集を始められる。
- [ ] 残件数から出したスケジュールを選ぶと、その編集を始められる。

### REQ-024

#### 受け入れ条件

- [ ] 日付を選ぶ前は、詳細は出ない。

- [ ] 詳細に出しきれないときは、詳細の中をスクロールして残らず見られる。

### REQ-025

画面が狭いとき、システムはスケジュールがある日に、その日の表示対象スケジュールのカテゴリ色を点で示すこと。日付の文字色は REQ-022 と同じ規則とする。詳細には、選んだ日の年月日と、日本の祝日名称およびユーザ休日の名称（あるとき）と、その日の表示対象スケジュールを出すこと。時間単位は、開始日では開始時分から終了時分とタイトル、開始日以外ではタイトルのみ。日単位はタイトル。

#### 受け入れ条件

- [ ] 表示対象のスケジュールが無い日には、点は出ない。
- [ ] 土曜日の日付は青、日曜日および休日の日付は赤である。
- [ ] 詳細の先頭に年月日が出る。祝日・ユーザ休日の名称があるときは付ける。
- [ ] 時間単位の開始日では `HH:MM ～ HH:MM` とタイトルで出る。
- [ ] 時間単位の開始日以外ではタイトルのみで出る。
- [ ] 日単位はタイトルで出る。
- [ ] 並びは REQ-019 に従う。
- [ ] TODO は予定と区別でき、実施済みは取り消し線で出る。
- [ ] 詳細から実施状態だけを変えることはできない。

### REQ-026

画面が狭いとき、利用者が詳細のスケジュールを選んだときはシステムはその編集を受け付けること。新規追加の操作を選んだときは、新規スケジュールの追加を受け付けること。

- [ ] 新規追加の操作を選ぶと、新規追加の入力を始められる。

- [ ] 日付を選んでいない状態で新規追加するとき、開始と終了の初期値は操作している日である。

### REQ-027

スケジュール・カテゴリ・ユーザ休日・表示設定の操作が試みられたとき、システムは当該試行の記録を log フォルダへ出力すること。

#### 受け入れ条件

- [ ] 追加・更新・削除・実施状態の変更・表示設定の変更・ユーザ休日の変更の試行が log フォルダ配下のファイルに残る。
- [ ] 記録にはタイムスタンプが含まれる。
- [ ] 記録には区分（INF、WRN、ERR、DBG のいずれか）が含まれる。
- [ ] 記録には、入力のうち判断に使う値が含まれる。
- [ ] 記録には判断結果（成功または失敗）が含まれる。
- [ ] 失敗のとき、画面へ出さない内部理由が記録に含まれる。
- [ ] ファイルはサイズが大きくなったら新しいファイルへ切り替わる。

### REQ-028

ログイン中の、本機能が割り当てられた利用者がユーザ休日を追加するとき、システムは当該利用者の休日として、年月日と名称を付けて追加すること。同一ユーザの未削除のユーザ休日と年月日が重複するときは、追加を拒否すること。

#### 受け入れ条件

- [ ] 年月日と名称を指定して追加できる。
- [ ] 名称は空では受け付けない。
- [ ] 同一ユーザの未削除のユーザ休日に同じ年月日があるときは失敗する。
- [ ] 他ユーザが同じ年月日を使っていても追加できる。
- [ ] 論理削除済みのユーザ休日と同じ年月日なら追加できる。
- [ ] 日本の祝日と同じ年月日でも追加できる。
- [ ] 追加したユーザ休日は、当該利用者の休日一覧とカレンダーに出る。
- [ ] 他ユーザの休日一覧とカレンダーには出ない。

### REQ-029

ログイン中の、本機能が割り当てられた利用者がユーザ休日を更新するとき、システムは当該利用者の未削除ユーザ休日の年月日と名称を更新できること。変更後の年月日が同一ユーザの別の未削除ユーザ休日と重複するときは、更新を拒否すること。

#### 受け入れ条件

- [ ] 未削除の自分のユーザ休日の年月日を変えられる。
- [ ] 未削除の自分のユーザ休日の名称を変えられる。
- [ ] 名称を空にはできない。
- [ ] 変更後の年月日が、同一ユーザの別の未削除ユーザ休日と同じときは失敗する。
- [ ] 年月日を変えずに名称だけ変えるときは成功する。
- [ ] 存在しない、論理削除済み、または他ユーザのユーザ休日の更新は失敗する。

### REQ-030

ログイン中の、本機能が割り当てられた利用者がユーザ休日を削除するとき、システムは当該ユーザ休日を論理削除すること。

#### 受け入れ条件

- [ ] 指定した自分の未削除ユーザ休日を論理削除できる。
- [ ] 削除したユーザ休日は休日一覧とカレンダーに出ない。
- [ ] 削除後もデータは残る。物理削除はしない。
- [ ] 存在しない、既に論理削除済み、または他ユーザのユーザ休日の削除は失敗する。

## 非機能要件

- 本機能の利用には認証を必須とする。利用可否は、ログイン中ユーザに本機能が割り当てられているかで判定する。他機能の API は使わない。
- スケジュール・カテゴリ・ユーザ休日・表示設定は、操作しているユーザ自身のものだけを対象とする。
- 削除は論理削除とし、物理削除はしない。
- 本機能は `portal` の Python を import しない。ログイン画面は本機能では提供しない（`portal` でログインする）。
- 操作の記録は、入力された内容、それを元にした判断結果、正常系ではない場合の理由を契機として出力する。
- ログはファイルサイズでローテーションする。上限サイズと世代数は、機能の `.env` で指定する。コードに埋め込まない。
- パスワードとセッション ID はログに出さない。
- 失敗時に画面へ出す文言は、内部の詳細な理由を含まない。内部理由はログにだけ残す。
- 祝日は日本の祝日（振替休日を含む）とする。ユーザ休日はそれとは別に、利用者本人が登録する。
- 日時の基準は日本標準時とする。

## 対象外

- ログイン画面、メニュー画面（`portal` が担う）
- 本機能の初期登録（機能マスタへの追加と、利用者への割当は運用コマンドで行う）
- 他ユーザとのスケジュール共有、公開、招待
- 毎週・毎月などの繰り返し
- 通知、リマインダー、メール連携
- 週表示・日表示（月カレンダー以外）
- スケジュールの論理削除の取り消し
- カテゴリの論理削除の取り消し
- ユーザ休日の論理削除の取り消し
- 検索、一覧専用画面、印刷、外部カレンダー連携
